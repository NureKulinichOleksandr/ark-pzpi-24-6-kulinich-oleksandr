2 ЗАВДАННЯ

Метою першої практичної роботи є дослідження основних рекомендацій щодо написання якісного та чистого коду в Java. На практиці показати рекомендації, та як вони впливають на розуміння написаного, та його легкість у маштабуванні.
Основні завдання:
    1. ознайомитись зі стандартами кодування мови програмування Java;
    2. дослідити основні рекомендації написання чистого коду на Java: стильові рекомендації, структури коду, принципи його рефакторингу, обробку помилок, тестування та документування коду;
    3. підготувати приклади коду, що демонструють застосування рекомендацій;
    4. підготувати презентацію з 12 слайдів;
    5. записати відео доповіді тривалістю 7-9 хвилин;
    6. оформити звіт українською мовою, включити опис виконання роботи, висновки, список джерел та додатки А, Б, В.











3 ОПИС ВИКОНАНОЇ РОБОТИ

	Для доповіді було обрано мову програмування Java. Це строго типізована, об’єктно-орієнтована мова програмування з автоматичним керуванням пам’яттю(GC), що виконується у віртуальній машині JVM.
	Java широко використовується для розробки серверних рішень, корпоративних систем та Android-застосунків. Через велику кодову базу та тривалий життєвий цикл Java-проєктів єдині правила оформлення коду мають особливе значення: код читають і змінюють набагато частіше, ніж пишуть.

	3.1 Використовуйте осмислені назви змінних, методів і класів

	Правильне іменування допомагає іншим розробникам легко зрозуміти призначення того чи іншого шматка коду. Уникайте абревіатур і коротких імен без значення. У Java діють усталені угоди: класи та інтерфейси — UpperCamelCase, методи та змінні — lowerCamelCase, константи — UPPER_SNAKE_CASE, пакети — малими літерами без підкреслень. Назви методів мають бути дієсловами, назви класів — іменниками.
	Приклад:
 1  // Поганий приклад
 2  static int f(int a) {
 3      return a * 2;
 4  }
 5
 6  // Гарний приклад
 7  static int multiplyByTwo(int number) {
 8      return number * 2;
 9  }
10
11  // Поганий приклад
12  class order_service {
13      int Max_cnt = 10;
14      double calc(double a, double b) { return a * b; }
15  }
16
17  // Гарний приклад
18  class OrderService {
19      private static final int MAX_ITEMS_COUNT = 10;
20
21      double calculateTotalPrice(double unitPrice, double quantity) {
22          return unitPrice * quantity;
23      }
24  }
	Компілятор Java не вимагає дотримання угод, але багато біблиотек, фреймворків та IDE покладаються на них. Наприклад JavaBeans розпізнає властивості за іменами getX/setX. Або у Inteliji Idea при натисканні Alt + Insert відкриєтиься генератор, який може створювати методи по типу getX/setX, та не давати створити дуплікати, якщо такі методи вже існують. Недотримання угод змушує читача витрачати час на розшифрування змісту, збільшує ймовірність помилок під час змін і ускладнює освоєння нових членів команди у кодовій базі. Змістовні імена роблять коментарі здебільшого непотрібними.

	3.2 Дотримуйтесь єдиного форматування коду

	Цей пункт про дотримання єдиних відступів у коді, обмеження довжини рядка до 80-100 символів, та не писати складні логічні конструкції у один рядок, одна інструкція в одному рядку та фігурні дужки навіть для однорядкових блоків if, for, while.

Приклад:
 1  // Поганий приклад
 2  if (user != null) return user.getName(); else return "unknown";
 3  for (int i = 0; i < n; i++) sum += values[i];
 4
 5  // Гарний приклад
 6  if (user != null) {
 7      return user.getName();
 8  } else {
 9      return "unknown";
10  }
11
12  for (int i = 0; i < n; i++) {
13      sum += values[i];
14  }

	Відсутність фігурних дужок, це доволі часте джерело помилок, наприклад під час додавання другого рядка до тіла if розробник може помилково вважати, що він також належить умові. Також одна інструкція в одному рядку сприяє код ревью через систему контролю версій. Форматування варто автоматизувати інструментами (google-java-format, форматер IDE).

	3.3 Дотримуйтесь структури файлу та пакетів

	Один публічний клас на один файл, назва файлу збігається з назвою класу. Порядок оголошень у файлі: спочатку package, далі імпорти, далі клас. Не використовувати імпорти з зірочкою, прибирати невикористані імпорти. Усередині класу: константи, поля, конструктори, публічні методи, приватні методи. Пакети організовуйте за призначенням (com.example.shop.order, com.example.shop.payment), а не за технічним типом усього підряд.

Приклад:
 1  // Поганий приклад
 2  import java.util.*;
 3  import java.io.*;
 4
 5  public class Shop {
 6      void process() { List<String> items = new ArrayList<>(); }
 7      private int count;
 8      public static final int LIMIT = 5;
 9  }
10
11  // Гарний приклад
12  package com.example.shop.order;
13
14  import java.util.ArrayList;
15  import java.util.List;
16
17  public class OrderProcessor {
18      public static final int ITEMS_LIMIT = 5;
19
20      private int processedCount;
21
22      public void process() {
23          List<String> items = new ArrayList<>();
24          // ...
25      }
26  }


	Явні імпорти показують залежності класу та запобігають конфліктам імен (наприклад, java.util.Date і java.sql.Date). Передбачуваний порядок елементів дозволяє швидко знаходити потрібне в будь-якому класі проєкту.



	3.4 Пишіть короткі методи з однією відповідальністю

	Метод має виконувати одну задачу на одному рівні абстракції. Якщо метод перевищує екран, містить глибоку вкладеність або коментарі-розділювачі «крок 1, крок 2», його слід розбити, винісши код по методам, за допомогою «Виділення методу» [5]. Обмежуйте кількість параметрів (бажано не більше 3–4 на метод), використовуйте «раннє повернення» замість глибокої вкладеності.

Приклад:
 1  // Поганий приклад
 2  void processOrder(Order order) {
 3      if (order != null) {
 4          if (!order.getItems().isEmpty()) {
 5              double total = 0;
 6              for (Item item : order.getItems()) {
 7                  total += item.getPrice() * item.getQuantity();
 8              }
 9              if (total > 1000) {
10                  total = total * 0.9;
11              }
12              order.setTotal(total);
13          }
14      }
15  }
16
17  // Гарний приклад
18  void processOrder(Order order) {
19      if (order == null || order.getItems().isEmpty()) {
20          return;
21      }
22      double total = calculateTotal(order.getItems());
23      order.setTotal(applyDiscount(total));
24  }
25
26  private double calculateTotal(List<Item> items) {
27      double total = 0;
28      for (Item item : items) {
29          total += item.getPrice() * item.getQuantity();
30      }
31      return total;
32  }
33
34  private double applyDiscount(double total) {
35      return total > DISCOUNT_THRESHOLD ? total * DISCOUNT_RATE : total;
36  }

	Малі методи легше читати, повторно використовувати й покривати модульними тестами: у прикладі calculateTotal та applyDiscount можуть тестуються окремо. Довгі методи з багатьма відповідальностями — основне джерело дефектів при змінах, адже зміна однієї частини логіки може непомітно зачепити іншу. Принцип єдиної відповідальності знижує вартість подальшої підтримки.

	3.5 Замінюйте «магічні числа» іменованими константами

	Літерали, значення яких не очевидне з контексту, слід виносити в константи private static final або в enum. Рядкові та числові «коди статусів» краще замінювати переліченнями.

 1  // Поганий приклад
 2  if (order.getStatus() == 2 && total > 1000) {
 3      total = total * 0.9;
 4  }
 5
 6  // Гарний приклад
 7  private static final double DISCOUNT_THRESHOLD = 1000.0;
 8  private static final double DISCOUNT_RATE = 0.9;
 9
10  enum OrderStatus { NEW, PAID, SHIPPED, CANCELLED }
11
12  if (order.getStatus() == OrderStatus.PAID && total > DISCOUNT_THRESHOLD) {
13      total = total * DISCOUNT_RATE;
14  }

	Читач не може здогадатися, що означає 2 чи 0.9, а зміна значення вимагає пошуку всіх входжень по коду — легко пропустити одне з них. enum у Java є типобезпечним: компілятор не дозволить передати довільне число замість статусу, а оператор switch над enum може перевірятися на повноту.

	3.6 Правильно обробляйте помилки

	Перехоплюйте конкретні типи винятків, а не Exception чи Throwable; ніколи не залишайте порожній блок catch; не використовуйте винятки для керування потоком виконання; для ресурсів застосовуйте try-with-resources; перевіряйте аргументи на початку методу (Objects.requireNonNull, IllegalArgumentException);

Приклад:
 1  // Поганий приклад
 2  BufferedReader reader = null;
 3  try {
 4  reader = new BufferedReader(new FileReader(path));
 5          return reader.readLine();
 6  } catch (Exception e) {
 7          // ignore
 8          } finally {
 9          try { reader.close(); } catch (Exception e) { }
10          }
11          return null;
12
13  // Гарний приклад
14          try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
15          return reader.readLine();
16  } catch (IOException e) {
17          throw new ConfigLoadException("Не вдалося прочитати файл: " + path, e);
18  }


	Проковтнуті винятки приховують реальну причину збою: програма продовжує працювати з некоректним станом, а помилка проявляється пізніше й у іншому місці, що значно ускладнює налагодження. try-with-resources гарантує закриття ресурсу навіть у разі виняткової ситуації та усуває громіздкі і схильні до помилок вкладені блоки finally. Збереження cause дає повний стек викликів у логах.

	3.7 Віддавайте перевагу незмінності та сучасним засобам мови

	Робіть поля final, де це можливо. Не надавайте сеттери без потреби; для простих об’єктів-обгорток для даних використовуйте record. Замість null для «відсутнього значення» застосовуйте Optional як тип результату методу; використовуйте var лише там, де тип очевидний із правої частини.

Приклад:
 1  // Поганий приклад
 2  public class Point {
 3      private int x;
 4      private int y;
 5
 6      public int getX() { return x; }
 7      public void setX(int x) { this.x = x; }
 8      public int getY() { return y; }
 9      public void setY(int y) { this.y = y; }
10      // + equals(), hashCode(), toString() вручну
11  }
12
13  // Гарний приклад
14  public record Point(int x, int y) { }
15
16  // Повернення Optional замість null
17  public Optional<User> findUserByEmail(String email) {
18      return Optional.ofNullable(users.get(email));
19  }

	Незмінні об’єкти потокобезпечні за своєю природою, їх безпечно використовувати як ключі у HashMap і передавати між компонентами без захисного копіювання [3]. record автоматично генерує конструктор, equals, hashCode і toString, зменшуючи обсяг шаблонного коду та ймовірність розбіжності цих методів. Optional явно сигналізує у сигнатурі методу, що результату може не бути, і знижує ризик NullPointerException.

	3.8 Програмуйте відносно інтерфейсів і використовуйте дженеріки

	Типи змінних, полів і параметрів оголошуйте через інтерфейси (List, Map, Set), а не через конкретні реалізації. Не використовуйте «сирі» типи (raw types) — завжди вказуйте параметри типу. Надавайте перевагу композиції над успадкуванням.

Приклад:
 1  // Поганий приклад
 2  ArrayList items = new ArrayList();
 3  items.add("apple");
 4  String first = (String) items.get(0);
 5
 6  // Гарний приклад
 7  List<String> items = new ArrayList<>();
 8  items.add("apple");
 9  String first = items.get(0);

	Узагальнення переносять перевірку типів із часу виконання на час компіляції: помилка ClassCastException стає помилкою компіляції. Оголошення через інтерфейс дозволяє змінити реалізацію (наприклад, ArrayList на LinkedList чи CopyOnWriteArrayList) без змін в усьому коді, що знижує зв’язність, та спрощує модифікацію коду.

	3.9 Враховуйте продуктивність там, де це справді важливо

	Не застосовуйте передчасну оптимізацію, але уникайте відомих неефективних конструкцій: конкатенація рядків у циклі (краще використати StringBuilder), зайве автоупаковування (Long замість long), повторне обчислення незмінних значень усередині циклу, вибір відповідної колекції (HashMap для пошуку за ключем замість перебору List).

Приклад:
 1  // Поганий приклад
 2  String result = "";
 3  for (String word : words) {
 4      result += word + ", ";
 5  }
 6
 7  Long sum = 0L;
 8  for (int i = 0; i < 1_000_000; i++) {
 9      sum += i;
10  }
11
12  // Гарний приклад
13  StringBuilder builder = new StringBuilder();
14  for (String word : words) {
15      builder.append(word).append(", ");
16  }
17  String result = builder.toString();
18
19  long sum = 0L;
20  for (int i = 0; i < 1_000_000; i++) {
21      sum += i;
22  }

	Рядки в Java незмінні, тому кожна конкатенація в циклі створює новий об’єкт і копіює вміст, що дає квадратичну складність за довжиною результату. Автоупаковування в циклі створює мільйони тимчасових об’єктів і навантажує GC. Водночас оптимізувати слід на основі вимірювань профілювальнику, а не інтуїції, щоб не погіршувати читабельність без користі [3].

	3.10 Документуйте код за допомогою Javadoc

	Усі публічні класи, інтерфейси та методи слід документувати коментарями Javadoc: короткий опис призначення, @param, @return, @throws. Коментар має пояснювати «чому» та контракт методу, а не повторювати те, що й так зрозуміло з коду.

Приклад:
 1  // Поганий приклад
 2  // множимо
 3  public double calc(double a, double b) {
 4      return a * b; // повертаємо результат
 5  }
 6
 7  // Гарний приклад
 8  /**
 9   * Обчислює вартість позиції замовлення.
10   *
11   * @param unitPrice ціна за одиницю товару, не може бути від’ємною
12   * @param quantity  кількість одиниць, додатне число
13   * @return загальна вартість позиції
14   * @throws IllegalArgumentException якщо ціна або кількість недопустимі
15   */
16  public double calculateItemCost(double unitPrice, double quantity) {
17      if (unitPrice < 0 || quantity <= 0) {
18          throw new IllegalArgumentException("Некоректні ціна або кількість");
19      }
20      return unitPrice * quantity;
21  }

	Javadoc автоматично перетворюється на HTML-документацію API та відображається у підказках IDE, тому є частиною контракту класу [7]. Коментарі, що дублюють код, швидко застарівають і вводять в оману. Задокументовані вимоги до аргументів і винятків знижують кількість помилок під час використання чужого коду.

	3.11 Покривайте код модульними тестами

	Для Java стандартом є Junit [6]. Тест має бути ізольованим, детермінованим, швидким і перевіряти одну поведінку. Назва тесту описує сценарій і очікуваний результат; структура — Arrange / Act / Assert.

Приклад:
 1  import static org.junit.jupiter.api.Assertions.assertEquals;
 2  import static org.junit.jupiter.api.Assertions.assertThrows;
 3
 4  import org.junit.jupiter.api.Test;
 5
 6  class OrderServiceTest {
 7
 8      private final OrderService service = new OrderService();
 9
10      @Test
11      void calculateItemCost_validInput_returnsProduct() {
12          double result = service.calculateItemCost(10.0, 3);
13
14          assertEquals(30.0, result, 0.0001);
15      }
16
17      @Test
18      void calculateItemCost_negativePrice_throwsException() {
19          assertThrows(IllegalArgumentException.class,
20                  () -> service.calculateItemCost(-1.0, 3));
21      }
22  }

	Модульні тести є страховкою при рефакторингу, не завжди виходить с першого разу сзінити код, не змінивши його поведінку, і довести  що код працює індентично попередньому можна лише автоматичною перевіркою [5].

	3.12 Програмні інструменти для аналізу якості коду

	Для автоматизації контролю дотримання рекомендацій у Java-проєктах використовуються такі інструменти:
    • PMD — статичний аналіз: невикористані змінні, порожні блоки catch, надто складні методи(рис. 3.1.);

      Рисунок 3.1 — PMD як розширення у Inteliji Idea.

    • Checkstyle — перевірка відповідності стилю кодування (наприклад, Google Style або Sun Checks): іменування, відступи, імпорти, довжина рядків;
    • SpotBugs — пошук потенційних дефектів у байт-коді (можливий NullPointerException, неправильне використання equals, тощо)
    • SonarQube / SonarLint — комплексна оцінка якості: дублювання коду, цикломатична складність, «запахи коду», технічний борг;
    • google-java-format та форматер IntelliJ IDEA — автоматичне форматування коду;
    • IntelliJ IDEA — вбудовані інспекції та автоматичні рефакторинги (Extract Method, Rename, Inline, Change Signature, тощо);
    • JUnit — тестування та вимірювання покриття коду тестами.

	3.13 Практичний приклад рефакторингу

	У додатках В.2 та В.3 наведено приклад коду до та після рефакторингу, що поєднує кілька розглянутих рекомендацій: осмислені імена, константи замість «магічних чисел», виділення методів, обробка вхідних даних, застосування record та enum. Поведінка програми при цьому не змінюється, що перевіряється модульними тестами (додаток В.4).

В.2 Приклад програмного коду після рефакторингу
GitHub репозиторій: https://github.com/NureKulinichOleksandr/ark-pzpi-24-6-kulinich-oleksandr/blob/main/Pract1/ark-pzpi-24-6-kulinich-oleksandr-pract1/OrderService.java
 1  package org.chivqsss.shop.order;
 2
 3  import java.util.List;
 4
 5  public class OrderService {
 6      private static final double DISCOUNT_THRESHOLD = 1000.0;
 7      private static final double DISCOUNT_RATE = 0.9;
 8
 9      /**
10       * Обчислює підсумкову вартість замовлення з урахуванням знижки.
11       *
12       * @param items  позиції замовлення, не може бути null
13       * @param status статус замовлення
14       * @return підсумкова вартість замовлення
15       */
16      public double calculateOrderTotal(List<OrderItem> items, OrderStatus status) {
17          if (items == null || items.isEmpty()) {
18              return 0.0;
19          }
20          double total = calculateItemsTotal(items);
21          return isDiscountApplicable(status, total) ? total * DISCOUNT_RATE : total;
22      }
23
24      private double calculateItemsTotal(List<OrderItem> items) {
25          double total = 0.0;
26          for (OrderItem item : items) {
27              total += item.price() * item.quantity();
28          }
29          return total;
30      }
31
32      private boolean isDiscountApplicable(OrderStatus status, double total) {
33          return status == OrderStatus.PAID && total > DISCOUNT_THRESHOLD;
34      }
35
36      public enum OrderStatus {NEW, PAID, SHIPPED, CANCELLED}
37
38      public record OrderItem(double price, int quantity) {
39      }
40  }
